生产者消息发送流程

发送过程涉及 main 线程和 Sender 线程：

  1. main 线程创建双端队列 RecordAccumulator，把消息发送到队列。
  2. Sender 线程不断从 RecordAccumulator 拉取消息，发送到 Kafka Broker。

几个关键参数：

  • batch.size（批次大小，默认 16k，数据积累到该值才发送）
  • linger.ms（未达到 batch.size 时最多等待的时间，默认 0）
  • buffer.memory（缓冲区总大小，默认 32m）

重要参数

参数 说明
bootstrap.servers 连接集群的 broker 地址清单，如 hadoop102:9092
key.serializer / value.serializer key、value 的序列化类，必须写全类名
buffer.memory RecordAccumulator 缓冲区总大小，默认 32m
batch.size 一批数据最大值，默认 16k，适当增大可提高吞吐量
linger.ms 未达到 batch.size 时最多等待时间，默认 0
acks 应答级别：0 不等落盘、1 Leader 收到即应答、-1(all) Leader+ISR 全部收到才应答
max.in.flight.requests.per.connection 最多未返回 ack 的请求数，默认 5
retries 失败重试次数，默认 int 最大值
enable.idempotence 是否开启幂等性，默认 true
compression.type 压缩方式，默认 none，可选 gzip/snappy/lz4/zstd

生产者分区

分区的好处：便于合理利用存储资源并实现负载均衡；生产者和消费者都可以以分区为单位并行处理，提高并行度。

分区策略

默认分区器 DefaultPartitioner 的规则：

  • 指明 partition，直接使用该值。
  • 没有 partition 但有 key，用 key 的 hash 值与分区数取余得到分区。
  • 没有 partition 也没有 key，采用 Sticky（黏性）分区：随机选一个分区并尽量一直使用，等批次满了或 linger.ms 到后，再随机换一个分区。

数据可靠性

ack 应答级别：acks=0 不等待落盘、acks=1 Leader 收到即应答、acks=-1（all）Leader 与 ISR 里所有节点都收到才应答。

  • 数据完全可靠条件：acks=-1 + 分区副本数 >= 2 + ISR 里应答的最小副本数（min.insync.replicas）>= 2。
  • acks=0 可靠性差效率高；acks=1 中等，适合普通日志；acks=-1 可靠性高效率低，适合和钱相关的数据。
  • ISR：和 Leader 保持同步的 Follower + Leader 集合，Follower 超时未同步会被踢出 ISR（阈值由 replica.lag.time.max.ms 控制，默认 30s）。

数据幂等性

  • 至少一次（AtLeastOnce）＝acks=-1 + 副本>=2 + min.insync.replicas>=2，能保证不丢但不能保证不重复。
  • 最多一次（AtMostOnce）＝acks=0，能保证不重复但不能保证不丢。
  • 精确一次（ExactlyOnce）＝幂等性 + 至少一次。

幂等性

开启参数 enable.idempotence 默认为 true。Broker 以 <PID, Partition, SeqNumber> 作为重复判断主键，相同主键的消息只持久化一条：PID 是 Kafka 每次重启都会重新分配的，Partition 表示分区号，SeqNumber 单调自增。所以幂等性只能在单分区单会话内保证不重复，跨分区、跨会话仍然可能重复。

生产者事务

事务的作用：把跨分区、跨会话（甚至跨 Topic）的一批消息绑定成一个整体，要么全部提交成功、要么全部失败回滚，从而比幂等性覆盖的范围更广，在复杂场景下保证精确一次（ExactlyOnce）。

什么时候用事务？举例来说：

  • 从 topic A 消费订单，处理完把结果写到 topic B，同时提交 offset：这三个动作希望一起成功或一起失败，避免出现“结果写了但 offset 没提交”导致的重复处理。
  • 一批数据要发往多个分区或多个 Topic：希望这批数据要么全部对外可见、要么全部不生效，配合消费者的 read_committed 隔离级别，只读到已经提交的数据。

开启事务必须先开启幂等性，并设置唯一的 transactional.id。设置了 transactional.id，即使客户端挂掉，重启后也能继续处理未完成的事务。

数据有序与乱序

Kafka 只能保证单个 Partition 内有序，不能保证整个 Topic 全局有序。

为什么 Partition 内有序

一个 Partition 本质上是一个追加日志（Append-only Log），消息按 offset 顺序追加、按 offset 顺序读取，所以分区内天然有序。但一个 Topic 通常有多个 Partition，消息会被分散到不同分区，分区与分区之间没有全局顺序。例如 P0 收到 A、C，P1 收到 B、D，消费时可能出现 A→C→B→D，而不是 A→B→C→D。

如何保证同一个业务有序

使用业务 ID 作为消息的 key，相同 key 的消息会被分到同一个分区（简单理解：hash(key) % 分区数），分区内有序就保证了该业务的数据有序：

注意：这只能保证同一个 key 内部有序，不同 key（如不同订单）之间仍然没有全局顺序。

生产者端也可能导致乱序

  • 多个请求并发发送时，网络延迟或重试可能让后发的消息先到达，导致分区内乱序。
  • max.in.flight.requests.per.connection 控制一个连接上允许同时存在的未完成请求数：1.x 之前要保证单分区有序，该值必须为 1；1.x 及以后未开启幂等时该值需为 1，开启幂等（enable.idempotence=true）时该值 <= 5 即可，服务端会缓存最近 5 个请求的元数据以便重新排序。
  • 重试也可能造成乱序和重复，开启幂等性后 Kafka 利用 ProducerId、ProducerEpoch、Sequence Number 来避免。
  • 注意：acks 解决的是”消息有没有可靠写入”，和有序性是两回事，acks=all 不等于保证有序。

消费者端也可能造成”业务上的乱序”

分区内有序不等于业务处理结果有序：如果消费者用线程池并发处理，即使消息按 A→B→C 到达，处理结果也可能是 B→C→A。同一业务需要串行处理时，消费者侧也要保持单线程或按 key 串行。

消费者组中每个消费者负责自己的分区，各分区消费互不干扰，但跨分区的全局顺序同样没有保证。

如何实现全局有序

最简单的方式是 Topic 只设置一个 Partition，整个 Topic 严格有序；但分区数为 1 会限制并行能力和吞吐量，生产环境很少这样做。实际开发按业务选择：

需求 方案
所有消息全局有序 1 个 Partition
同一个用户有序 userId 作为 Key
同一个订单有序 orderId 作为 Key
同一个设备有序 deviceId 作为 Key
同一业务 Key 串行处理 相同 Key → 同 Partition + 消费者侧串行处理
不要求顺序 多 Partition

总结

  • Partition 内有序，Partition 之间无序。
  • 同一业务用业务 ID 作为 Key，保证进入同一分区，从而有序。
  • 全局有序只能靠单个 Partition 实现，但会牺牲并行能力和吞吐量。
  • Kafka 的设计理念不是追求全局有序，而是用 Partition 平衡”有序性”和”并行性”。
