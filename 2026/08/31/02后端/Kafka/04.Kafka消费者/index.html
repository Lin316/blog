消费方式

Kafka 采用 pull（拉）模式，消费者主动从 broker 拉取数据。优点是由消费者自己控制消费速率；缺点是数据不足时可能反复返回空数据。

消费者工作流程

消费者组原理

消费者组（CG）由多个 consumer 组成，条件是把 group.id 设为相同。

  • 组内每个消费者负责消费不同分区的数据，一个分区只能由一个组内消费者消费。
  • 消费者组之间互不影响；所有消费者都属于某个消费者组。
  • 如果组内消费者数量超过主题分区数，多出的消费者会闲置，不接收消息。

消费者组初始化：每个消费者先发 JoinGroup 请求，协调者（Coordinator）选出一个 leader 消费者，由它制定消费方案，再通过 Coordinator 下发给每个消费者。

  • coordinator 选择：groupid 的 hashcode % 50，落在 __consumer_offsets 的对应分区所在的 broker 上。
  • 每个消费者与 Coordinator 保持心跳（默认 3s），超时（session.timeout.ms=45s）或处理消息过长（max.poll.interval.ms=5min）会被移除并触发再平衡。

消费者重要参数

参数 说明
bootstrap.servers 连接集群的 broker 地址清单
key.deserializer / value.deserializer key、value 的反序列化类，必须写全类名
group.id 消费者所属的消费者组，必须配置
enable.auto.commit 是否自动提交 offset，默认 true
auto.commit.interval.ms 自动提交 offset 的频率，默认 5s
auto.offset.reset 无初始 offset 时：earliest 从最早、latest 从最新、none 抛异常
heartbeat.interval.ms 与 coordinator 的心跳时间，默认 3s
session.timeout.ms 与 coordinator 连接超时时间，默认 45s
max.poll.interval.ms 处理消息最大时长，默认 5 分钟
fetch.min.bytes 一批消息最小字节数，默认 1 字节
fetch.max.wait.ms 未达到最小字节数的最长等待，默认 500ms
max.poll.records 一次 poll 拉取的最大条数，默认 500 条

分区分配与再平衡

Kafka 有四种分区分配策略：Range、RoundRobin、Sticky、CooperativeSticky，通过 partition.assignment.strategy 配置，默认是 Range + CooperativeSticky。

  • Range：针对每个 topic，把分区排序后按消费者数量平均分配，除不尽时靠前的消费者多分 1 个；topic 多时容易造成数据倾斜。
  • RoundRobin：把集群中所有 topic 的所有分区和消费者列出，排序后轮询分配，各消费者分区数更均衡。
  • Sticky：分配带有”粘性”，尽量保持上一次分配结果不变，减少再平衡开销。

offset 位移

  • 0.9 版本之后，offset 默认保存在 Kafka 内置主题 __consumer_offsets 中；之前保存在 Zookeeper。
  • __consumer_offsets 用 key = group.id + topic + 分区号、value = 当前 offset 存储，并定期 compact。

自动提交

手动提交

开启手动提交需设置 enable.auto.commit=false。两种方式：

  • commitSync（同步）：提交完才消费下一批，有失败重试，更可靠但效率低。
  • commitAsync（异步）：发出提交请求就继续消费，效率高，但可能提交失败。

指定 offset 消费

当 Kafka 中没有初始偏移量（消费者组第一次消费）或服务器上不再存在当前偏移量时（例如数据已被删除），由 auto.offset.reset 决定怎么处理，默认是 latest：

auto.offset.reset 说明
earliest 自动将偏移量重置为最早的偏移量，从头开始消费（等价于命令行的 –from-beginning）
latest 默认值，自动将偏移量重置为最新偏移量，只消费新数据
none 如果未找到消费者组的先前偏移量，则向消费者抛出异常

漏消费和重复消费

  • 重复消费：已消费但 offset 没提交（如自动提交间隔内消费者挂了）。
  • 漏消费：先提交 offset 后消费，提交后数据还在内存未落盘时消费者挂掉，导致数据丢失。

要做到既不漏也不重，需要消费者事务，把消费和提交 offset 做原子绑定（如把 offset 存到支持事务的 MySQL）。

数据积压

消费能力不足时：

  • 如果是 kafka 消费能力不足，增加 topic 分区数，并同时增加同组消费者数量（消费者数 = 分区数）。
  • 如果是下游处理不及时，提高每批次拉取数量，如调大 max.poll.records（默认 500）。
