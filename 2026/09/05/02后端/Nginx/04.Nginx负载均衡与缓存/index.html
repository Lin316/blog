负载均衡概述

单台服务器的处理能力存在上限，且存在单点故障风险。系统扩展可分为两类：

方式 说明 特点
纵向扩展（Scale Up） 提升单机 CPU、内存、磁盘等硬件能力 存在硬件天花板，成本非线性增长
横向扩展（Scale Out） 增加服务器数量组成集群 可平滑扩容，需引入负载均衡

横向扩展涉及两个角色：

  • 应用集群：同一应用部署于多台服务器，共同处理请求；
  • 负载均衡器：依据调度算法将请求分发至集群中的某一节点。

负载均衡的价值包括：缓解高并发压力、实现故障转移、支持水平扩容，并可在入口层实施安全过滤。

常见负载均衡方式

方式 原理 优点 缺点
用户手动选择 页面提供多个入口由用户自选 实现简单 依赖用户，无法自动调度
DNS 轮询 域名配置多条 A 记录，解析时轮流返回不同 IP 成本低、易配置 可靠性差、分配不均（不感知节点状态与性能）
四/七层负载均衡 负载均衡器按 IP+端口或 URL/域名分发 调度可控、支持故障转移 需额外部署组件

生产环境常见组合为四层采用 LVS、七层采用 Nginx（或 HAProxy）。

四层与七层负载均衡

四层 七层
作用层级 传输层（OSI 第 4 层） 应用层（OSI 第 7 层）
调度依据 IP + 端口（TCP/UDP） URL、域名、请求头等
效率 较高 相对较低
是否识别域名 否 是

四层负载均衡在底层完成数据包分发，效率更高；七层负载均衡可基于业务内容精细化调度。

六种调度策略

策略 配置写法 调度规则 适用场景
轮询 默认 按顺序轮流分发 节点配置均衡、请求耗时接近
加权轮询 weight=数字 按权重比例分发 节点性能存在差异
ip_hash ip_hash; 同一客户端 IP 固定分发至同一节点 会话保持
least_conn least_conn; 分发至当前连接数最少的节点 请求耗时差异较大
url_hash hash $request_uri; 同一 URI 固定分发至同一节点 提升后端缓存命中率
fair fair;（第三方） 分发至响应时间短的节点 节点性能动态变化

Nginx 四层负载均衡（stream）

Nginx 1.9 起提供 stream 模块，可对 TCP/UDP 流量进行转发与负载均衡，适用于 Redis、MySQL 等非 HTTP 服务。该模块默认未编译，需通过 ./configure --with-stream 启用。

Nginx Web 缓存

缓存机制

缓存指在客户端与应用服务器之间保存响应副本，相同请求再次到达时直接返回副本，减少对后端的访问。其优势在于降低网络传输、减轻后端压力、提升响应速度；代价是可能产生数据不一致，并增加存储开销。

Nginx 自 0.7.48 起提供缓存能力，基于 Proxy Store 实现：将 URL 等组合信息作为 Key，经 MD5 哈希映射为磁盘目录路径，缓存内容保存于对应目录。

指令速查

指令 作用
proxy_cache zone_name 开启缓存并指定缓存区
proxy_cache_key key 自定义缓存 Key
proxy_cache_valid 200 5d 按响应状态码设置缓存时长
proxy_cache_min_uses 5 被访问指定次数后才写入缓存
proxy_cache_methods 缓存的请求方法（默认 GET/HEAD，POST 不缓存）

设置不缓存

频繁变化的数据不适合缓存，可通过两个指令控制：

  • proxy_no_cache：满足条件时不写入缓存；
  • proxy_cache_bypass：满足条件时绕过缓存直接请求后端。
